## QA Mobile API bank fixture (auto-generated by the bank-feed mock)

When a test application is created via the Mobile API signup flow
(`POST /api/v1/application/{id}/bankstatements/default` with `InstitutionSlug: "nab"`), the
**server side bank-feed mock** returns a synthetic bank account that is persisted to
`dbo.ApplicationBank` and exposed via `GET /api/v1/application/{id}/bankaccounts`. The
automation framework reads `accounts[0]` and POSTs it back to `/api/v1/bankaccount`.

| Field | Value |
| --- | --- |
| BankName | Bank of Queensland |
| SortCode (BSB) | 123456 |
| AccountName | Mary Jones |
| AccountNumber | encrypted at rest in `dbo.ApplicationBank.AccountNumberEncrypted` |

Caveats recorded on the page:

- The fixture is **server side**. It is not in any local repo (Amortization, Tools.Automation,
  Libraries, Mobile.Api). Searching the codebase for "Bank of Queensland" or "123456" returns
  zero hits; query the DB instead
  (`SELECT * FROM dbo.ApplicationBank WHERE ApplicationId = ...`).
- `dbo.CustomerBank` is **unused for QA test customers**; only `dbo.ApplicationBank` carries
  the record.
- This fixture is used by `Wagtestfundautopool*` customers (PoolService) and every other
  Mobile API signup flow test. As of 2026-05-15, about **84% of QA apps with a bank record
  carry this fixture**.
- Contrast with the APY dealership flow: the APY automation suite submits the documented
  `MMMFG Autopay Trans / 062104` fixture directly via the dealer portal UI, bypassing the
  bank-feed mock.
- Why it matters: in the 2026-05-12 outage the QA Zepto test fund source ran out and every
  Mobile API signup test app was rejected with status `91004, "Your bank account has
  insufficient funds"`. Because 84% of QA test apps share one fixture, a single Zepto side
  issue blocks the entire test estate.
- References: `MmeApiApplicationGenerator.cs:721-758`; database `dbo.ApplicationBank` in
  `Horizon2_QA`; "How an Application Becomes Eligible to Fund", TECHNOLOGY page 2785771528;
  incident QAAUTO-1148.

## Production testing, test flag naming

| Flag pattern | Meaning |
| --- | --- |
| `wagtestfundxxx` (xxx unique) | Default risk band is B. Example `_wagtestfund_mel011623qa1` |
| `wagtestscorexxx-score` (xxx unique, score = risk band) | Veda Score 900, Risk Band AA. Example `_wagtestscore_mel011623qa2-900` |
| `wagtestscorevedaaxxx-score` (xxx unique) | Veda Score 900, Risk Band AA. Used when testing Decision Engine Access Seeker related paths |

This is the same `wagtest*` naming that App Support filters out of the funding and refund sweep
queries (`C.FirstName NOT LIKE '%wagtest%'`), and the same naming behind the MHD-35810 /
PER-8863 pattern where a `wagtest*` customer squats a production username.
